Raqib

A read only lookout over your cloud access, for AWS, Azure, GCP, and Kubernetes. It finds the paths an attacker would take, and tells you how to close them.
GitHub Open a sample report

What it does

Raqib reads the authorization export your account already produces, for AWS, Azure, GCP, or Kubernetes, and reports the exposure in it, organized by the moves an intruder makes after a foothold. It is built as the mirror of an offensive toolkit that runs across the same four clouds: for each tactic an attacker runs, Raqib reads the account for the weakness that lets it work, and tells you the change that closes it.

It never calls a cloud and never touches your account. You hand it a file, and it reasons about that file offline. Nothing to trust it with beyond a JSON export you control.

Run it

Produce your cloud's authorization export and audit it. Raqib detects the cloud on its own. The AWS quickstart:

aws iam get-account-authorization-details > export.json
python3 raqib.py audit export.json

# add credential findings, and write a shareable HTML report
aws iam generate-credential-report && aws iam get-credential-report --query Content --output text | base64 --decode > creds.csv
python3 raqib.py audit export.json --credential-report creds.csv -o report.html

# gate a pipeline: exit 1 on a critical or high finding
python3 raqib.py audit export.json --strict

It is a single zero dependency Python tool. It needs Python 3.8 or newer and nothing else.

Four clouds, six tactics

Raqib reads AWS, Azure, GCP, and Kubernetes, and reports the same six attacker tactics in each cloud's own terms. The checks are named by tactic and cloud, in a matrix that mirrors the offensive framework module for module. Run python3 raqib.py defends for the map.

  • Reconnaissance: the mapping done first, dumping the IAM configuration in AWS, Reader over a management group in Azure, project Viewer in GCP, cluster wide list in Kubernetes.
  • Privilege escalation: IAM escalation paths and administrator in AWS, Owner and writing role assignments in Azure, Owner and setIamPolicy and impersonation in GCP, cluster-admin and the escalate, bind, and impersonate verbs in Kubernetes.
  • Persistence: creating an identity and granting it access, creating service account keys, creating cluster role bindings and admission webhooks.
  • Lateral movement: trust that lets the wrong caller in, a role granted to everyone, a service principal with broad reach, reading secrets that hold service account tokens.
  • Exfiltration: reading secrets, objects, parameters, and keys broadly, listing storage keys, reading config maps and secrets across a cluster.
  • Anti forensics: stopping or deleting the account's own logging, in each cloud.

Every finding carries the MITRE ATT&CK technique it defends against. AWS is the deepest today; Azure, GCP, and Kubernetes cover the primary paths and have room to grow.

A finding says what a permission would allow, not that it was used. A clean report means the export named nothing these rules look for, not that the account is secure. Read only analysis by Raqib.
